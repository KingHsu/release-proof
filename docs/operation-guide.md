# ReleaseProof 明细操作手册

本文只讲怎样亲自运行、怎样构造“证据充分”和“证据不足”两类正常结果，以及 API 模式到底改变了什么。

## 1. 先认识五种建议

| 建议 | 是否程序故障 | 含义 |
|---|---:|---|
| `ready_for_human_review` | 否 | 每条验收条件都有实现证据和验证证据，可以进入人工发布评审 |
| `conditional` | 否 | 自动证据基本成立，但仍有兼容性、回滚或其他人工检查 |
| `not_ready` | 否 | 至少一条验收条件缺少直接实现或验证证据，暂不建议发布 |
| `insufficient_evidence` | 否 | 报告引用的证据缺失、被修改或不足以形成可信结论 |
| `analysis_failed` | 是 | 必需取证器失败或工作流无法形成验收条件 |

`ready_for_human_review` 也不是“系统批准上线”。ReleaseProof 的最高权限只是把材料交给人评审。

## 2. 启动

双击项目根目录的 `start-release-proof.cmd`。首次缺少 `.venv` 时启动器会在本项目内准备环境，以后直接复用。

菜单提供：

1. 内置证据充分案例；
2. 内置证据不足案例；
3. 验收本地 Git 项目；
0. 退出。

两个内置案例使用同一类只读 Git Diff 和 JUnit 报告，只改变“需求是否真的被这些证据支持”，因此失败结果不是程序故障。

## 3. 无 API：零费用对照

### 3.1 证据充分

1. 选择 `1`。
2. “使用真实 DeepSeek Planner”输入 `n` 或直接回车。
3. 观察 Planner 依次选择 `read_diff`、`read_test_report`。
4. 观察 Harness 执行工具，矩阵得到 1 条实现证据和 1 条验证证据。

预期建议：`ready_for_human_review`，中文显示“可以进入人工评审”。

### 3.2 证据不足

1. 选择 `2`。
2. DeepSeek 选择 `n`。
3. 案例需求要求“导出的账户报告包含 id 和 total 列”，但仓库变更和测试只证明健康状态返回 ok。

预期建议：`not_ready`。这证明“测试通过”不等于“测试覆盖了本次需求”。

## 4. 有 API：真实 DeepSeek Planner

内置案例和本地项目都可以选择真实模式：

1. 在“使用真实 DeepSeek Planner”处输入 `y`；
2. 阅读费用提示；
3. 输入大写 `ONLINE`。

单次分析最多 4 次模型请求，重试为 0。模型负责提取验收条件和提出下一步只读工具；Harness 决定工具能否执行，Policy Gate 决定证据上限。

### 4.1 API + 证据充分

选择菜单 `1 → y → ONLINE`。正常情况下最终仍是 `ready_for_human_review`。如果某次 DeepSeek 结构化输出不合格，run 级熔断会切换到离线 Planner，报告会在 limitations 中如实记录降级，而不会伪造工具已执行。

### 4.2 API + 证据不足

选择菜单 `2 → y → ONLINE`。模型可以建议去读 Diff 和测试，但不能把不相关的健康检查包装成账户报表证据，确定性矩阵仍应得到 `not_ready`。

API 模式证明真实结构化规划链路；它不应该改变证据事实，也不保证比离线模式更容易“通过”。

## 5. 验收自己的本地 Git 项目

选择菜单 `3`，依次提供：

1. Git 仓库绝对路径；
2. 一条可验证的验收要求；
3. 仓库内机器可读测试报告路径，可留空；
4. 是否使用 DeepSeek。

好的要求：

```text
点击查询后必须显示答案、原文引用和文档版本号。
```

不好的要求：

```text
AI 功能是完善的，核心体验是完成了的，基本功能是完成了的。
```

后者没有可观察行为、输入、输出或边界。CLI 现在会在调用付费模型之前提示改写；默认取消，避免浪费额度。

测试报告必须是仓库内路径，例如：

```text
reports/junit.xml
```

只写“测试已通过”不能进入验证证据层，因为系统无法确定是谁观察、验证了什么、是否零失败。

## 6. 本次 `7489...` 报告为什么是 not_ready

报告中的可核对事实：

1. 三条要求都是“完善/完成”这类不可验证形容词，并被标记为关键条件；
2. Diff 只有 `scripts/start_web.py` 和 `tests/test_web_launcher.py`；
3. 没有机器可读测试或 CI 证据进入 Ledger；
4. 在线 Planner 有一次结构化 schema 失败，系统熔断并转为离线 Planner；
5. 全程发生 4 次模型调用，但没有任何模型输出能越过证据门禁；
6. 三条关键条件均为 `unsupported`，所以 Policy Gate 必须返回 `not_ready`。

这不是“Agent 没发挥作用”，恰恰说明它没有因为用户说“完成了”就替用户编造完成证据。问题主要在输入需求不可验收，其次是缺少直接测试报告。

## 7. 面试演示顺序

1. 用菜单 1 展示 Planner → Harness → Ledger → Matrix → Policy Gate。
2. 用菜单 2 展示为什么不相关测试不能给需求背书。
3. 解释在线模型失败时的 circuit breaker 和离线降级。
4. 强调最高结果只是进入人工评审，不是自动发布。

现场优先用离线模式，结果稳定且零成本；真实 DeepSeek 历史轨迹用于证明在线 Planner 确实接通过。
